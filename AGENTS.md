# databricks-sql-quickcheck

Guidance for AI coding agents working in this repo. The workspace index is
`../AGENTS.md`. Read that first for the standing constraints, which apply here
too: no employer SQL, ever, and no work compute.

Last updated 2026-09-26 (truncated-statement and empty-list checks; the
silence-by-default rule and the forbidden-adjacency design).

## What this is

This is a fast, shallow syntax checker for Databricks SQL. It is a single-pass
lexer plus structural checks, written in TypeScript with no runtime
dependencies, and it ships as three things: a VS Code extension, a CLI and a
library. It is the as-you-type tier. SQLFluff (`../sqlfluff`) is the
full-grammar tier, run on save or in CI.

```
src/lexer.ts      token boundaries: strings, quoted identifiers, comments, $$ bodies,
                  templates, notebook cell separators. Nothing statement-level.
src/check.ts      token-level checks (brackets, commas, operators, lists), run per fragment
                  (tokens between `;` / cell separators)
src/statements.ts statement-shape checks: keyword typos, missing `;`, column-definition
                  commas, clause order, CASE structure, dangling keywords,
                  truncated statements (`ALTER VIEW v RENAME TO`, `DROP SCHEMA`),
                  empty clause lists (`SET DBPROPERTIES ()`)
src/common.ts     shared types and token helpers
src/keywords.ts   GENERATED by scripts/gen_keywords.py -- do not edit by hand
src/cli.ts        dbsql-quickcheck: files, --stdin, --json, --jsonl batch mode
src/extension.ts  VS Code: diagnostics on open/change (40 ms debounce), in-process
src/test/         node:test unit tests
eval/evaluate.py  the corpus evaluation (run with ../databricks-sql-corpus/.venv)
docs/design-notes.md  why the rules below are the rules: the silence-by-default
                  property, the two designs that fail it, the forbidden-adjacency
                  skeleton and its admission gates
scripts/derive_shape_sets.py  re-derives and safety-checks NEEDS_FOLLOWER and
                  EMPTY_LIST_OWNERS against every valid source
examples/         mistakes.sql: one mistake per statement, the README's sample output
```

## The invariant, and the rule that follows from it

**An error must never fire on valid SQL.** A false positive on every keystroke
is worse than no checker. Before any change to `lexer.ts`, `check.ts` or the
keyword list is done:

```bash
npm test
../databricks-sql-corpus/.venv/bin/python eval/evaluate.py
```

**Unrecognised input must produce silence, not a finding.** A finding needs
positive evidence of a violation; the absence of a matching rule is not evidence.
This is the rule that earlier versions of this file wrote as "don't grow this
into a grammar" -- which was shorthand, and shorthand that forbids a *shape*
rather than a *failure mode* will eventually block the right change for the wrong
reason. Productions, a recursive descent, even a parse tree are all allowed. What
is forbidden is any design whose default verdict on syntax it has not been taught
is "invalid".

Both tempting designs fail that test, and both failures are measured in
`docs/design-notes.md`: a full grammar cannot parse 58 of the corpus's 562 valid
published files as released (10 at the best ceiling that exists anywhere), and
21.8% of valid statements contain a keyword adjacency found nowhere else in the
corpus, so "unseen, therefore wrong" fires on one valid statement in five. Read
that file before adding a check that generalises, and before relaxing this rule.

The evaluation must still report `0` error files and `0` warning files on the
valid corpus, and `823/823` clean must-parse reference cases (the count grows
as the corpus does). Its exit status is non-zero on any false positive, and 2
if its known-bad control stops firing. It also reports catch rates. On the
corpus's own `mutate.py` mutants the guaranteed tier is at 100.0%. On
everyday mistakes made to the clean files it is 95% of keyword typos, 94% of
deleted `;` and 96% of deleted column commas (all as of 2026-09-26). A change
that trades a false positive for recall is the wrong trade.

**The must-reject cases are split by shape, and only one half is ours.** The
reference corpus has 395 of them and a single catch rate over all 395 is
misleading, because most of what it counts is grammar-level and out of remit.
`shape_of` in the evaluation buckets each case:

| bucket | meaning | whose |
| --- | --- | --- |
| `truncated` | stops on a keyword or operator still owing an operand | ours |
| `empty-list` | a *clause* bracket with nothing in it | ours |
| `grammar` | well-formed shape, a required clause missing | SQLFluff's |

`-> target` is the line to watch: the two structural buckets together. It went
from **40/219 (18.3%) to 155/219 (70.8%) on 2026-09-26**, and the overall
must-reject figure from 71/395 to 187/395, by mining cases the corpus already
had rather than by generating new ones. The `grammar` bucket sits at 18% and
is not a target: about 90 of the 395 are missing *values* inside a slot
(`column_comment`, `data_type`, `expr`), which no shallow checker should read.
The honest ceiling is ~280/395; `docs/design-notes.md` derives it.

`empty-list` counts a bracket only when a *keyword* owns it. `CREATE FUNCTION
f()` and `SELECT uuid()` write an empty pair legitimately, so counting every
`()` would put cases in our tier that no shallow checker should ever flag.

Also run the adversarial pass over Spark's own test suite (`spark-sql-tests`,
304 files of unusual syntax, unscored because it mixes valid and invalid
statements). It is where the `EXPLAIN FORMATTED` newline and
pipe-`AGGREGATE` alias false positives were found, and no other set had them --
and on 2026-09-26 it earned its keep again, catching three false positives in
the first cut of the truncated-statement check (see below). It now reports
five errors, all real; the only one from the new checks is `cast.sql:178`,
which sits under that file's own "negative tests" heading.

The first version was tuned only against `mutate.py` and scored 100% there,
but it caught 7 of 30 everyday mistakes when Tom typed into a real file. The
mutation generator only makes bracket, quote, comma and operator damage.
Measure against mistakes people make (`everyday_mutants` in the evaluation),
not only against the generator you have.

Every check needs two tests: a case that must fire, and the valid Databricks
construct that looks most like the mistake, which must stay quiet. Examples:
`ARRAY<INT>)` next to `a >)`, `count(*) total` next to `a b c`.

## Severity

- **error**: no grammar can accept it (brackets, quotes, `,,`, a dangling
  operator, `CASE` without `END`).
- **warning**: Spark's non-reserved keywords mean the parser might accept it
  (`SELECT a, FROM t` can read as a column named `from`), or it is valid SQL
  that does the wrong thing (`SELECT a\n  b`).

Heuristic checks are warnings. They only run on fragments with no errors,
because they depend on bracket depths.

## Things that cost time to get right

- **A word one letter off a keyword proves nothing on its own.** Databricks
  lets nearly every keyword be a name, and real schemas have columns called
  `form`, `pull`, `target`, `name`. A typo is reported only with positional
  evidence:
  - between two complete operands, where no name can go (`SELECT a FORM t`);
  - before a word that only follows a keyword (`ORDRE BY`, `CAES WHEN`);
  - after a keyword whose next word is fixed (`LEFT JION`, `IS NUL`).

  `CONTINUES` (keywords that cannot end an expression) and `STRUCTURAL`
  (keywords that cannot begin one) in `statements.ts` define "operand" as a
  blocklist, precisely because so many keywords are used as names.
- **A keyword at the end of a statement is often the object's own name.**
  This is the same trap as the typo rule above, and it bit three times in one
  afternoon. Spark's own suite writes `DROP VIEW view` and `SHOW TBLPROPERTIES
  view`, and `SHOW CURRENT SCHEMA` is a real statement -- all three fired in
  the first cut of the truncated-statement check. Three guards, all needed:
  - `NEEDS_FOLLOWER` holds only syntax glue that owes something whatever
    precedes it (`AS`, `RENAME TO`, `LIMIT`). Membership is the opposite trade
    from `KEYWORDS`: an extra word here is a false positive, not a lost catch.
  - `NEEDS_FOLLOWER_AFTER_NAME` (`COMMENT`, `LOCATION`) fires only in DDL and
    only after a name or `)`. `CREATE SCHEMA s COMMENT` is truncated;
    `ALTER TABLE t DROP COLUMN location` is a column called `location`, and
    the token before is what separates them.
  - the object-type rule needs the type to follow the verb or a known
    modifier, *and* the statement to name nothing at all. `DROP VIEW` fires;
    `DROP VIEW view` does not.

  `CATALOG` is deliberately not an object type: its name is optional in every
  production that takes it, so `USE CATALOG` and `SHOW GRANTS ON CATALOG` both
  parse and are must-parse cases. `ON`, `IN` and `TO` are not modifiers, because
  each also precedes a name (`GRANT SELECT ON view`).

  After touching either set, run
  `../databricks-sql-corpus/.venv/bin/python scripts/derive_shape_sets.py`.
  It re-derives the candidates from the reference corpus and fails if a word
  already shipped now ends a valid statement anywhere in the 866 corpus files,
  the must-parse cases or spark-sql-tests.

  **The spark-sql-tests veto is too strong and should be advisory.** That source
  deliberately contains invalid SQL, so it vetoes candidates the docs say are
  invalid -- `SELECT * EXCEPT ( )`, `RETURNS TABLE ( )`, `tablesample ( )` and
  `SHOW TABLE EXTENDED` are all vetoed by it while the reference corpus labels
  the identical shape must-reject. Fail only when no must-reject case
  contradicts the veto. It is the right tool for finding false positives by
  running the checks over it, and the wrong tool as a validity oracle.

- **The invalid corpus you need may already exist.** Before building a
  generator, check what is unmined. In September 2026 the plan was a better
  `mutate.py`; measuring first showed it was saturated (100% caught on every
  guaranteed kind) while 323 of the reference corpus's 395 must-reject cases
  had never been looked at, two thirds of them structurally reachable. Mining
  those moved the target metric 18% -> 71% with no generator at all.

- **A same-line implicit alias (`SELECT a b, c`) is not warned by default.**
  250 deliberate uses were found in 50 of 510 valid files. It is opt-in
  (`explicitAliases`) for teams that require AS.
- **`Chapter08/Clean Up.sql` is broken as published.** Its `USE CATALOG` has no
  `;` before the next statement. The corpus's `docs/gaps.md` records it as a
  source-side error, and SQLFluff agrees. `KNOWN_BROKEN` in the evaluation
  scores it the other way round (quickcheck must flag it). Add a file there
  only with that kind of independent confirmation.

- **Keywords decide the missing-comma heuristics.** A word in `KEYWORDS` is
  never treated as a bare identifier, so a word missing from the set can cause
  false positives. `OFFSET` and `MEASURES` did, because SQLFluff's lists lack
  them. An extra word only costs recall. Add words to `EXTRA` in
  `scripts/gen_keywords.py` and regenerate with `npm run keywords`. Don't add
  common column names (`ID`, `NAME`, `VALUE`).
- **An alias on a new line is only a warning after a bare column.** TPC-DS
  writes `sum(case … end)` then `sun_sales` on the next line on purpose.
- **Notebook cells are hard boundaries.** Each cell runs on its own, so the
  lexer stops strings and comments at `-- COMMAND ----------`, but only in
  files with the `-- Databricks notebook source` header.
- **`SET key = value` is raw text to Spark.** `SET foo = (1, 3` is valid, so
  raw statements (`SET`, `RESET`, `ADD`, `LIST`, `REFRESH`, `DFS`) get lexical
  checks only. `SET VAR` is real SQL and is checked.
- **Hints are parsed by Spark.** `/*+ BROADCAST(t) */` is a comment to the
  lexer, but its brackets are checked when it follows
  `SELECT`/`INSERT`/`UPDATE`/`MERGE`/`DELETE`.
- **`mutate.py` mis-tiers `SET` mutants after a notebook header.** Its
  `_in_set_statement` doesn't skip SQLFluff's `notebook_start` token. The
  evaluation excludes those mutants explicitly, with a printed count, rather
  than scoring them. The one-line fix belongs in databricks-sql-corpus.

## Known and unfixed

Found 2026-09-26 while designing the adjacency check, left for a follow-up.
All three cost catches; none can cause a false positive, which is why the
gates are green with them present.

- **`GRANT`/`REVOKE`/`DENY` return before the shape checks run.**
  `checkStatements` bails out early for these leads, because privilege lists
  (`GRANT SELECT, MODIFY ON ...`) confuse `columnDefinitions` and
  `clauseOrder`. The return sits above `truncatedStatement()` and
  `emptyLists()`, so `GRANT SELECT ON TABLE t TO` and
  `REVOKE SELECT ON TABLE t FROM` stay silent even though `TO` and `FROM` are
  both in `NEEDS_FOLLOWER`. Move the return below them. Four must-reject cases.
- **`AS OF` is invisible to `isKw`.** `isNameContext` treats a preceding `AS`
  as making the next word a name, which is right for aliases and wrong for the
  fixed pair `AS OF`. `RESTORE TABLE t TO VERSION AS OF` therefore does not
  fire despite `OF` being in `NEEDS_FOLLOWER`. Two cases.
- **`ZORDER BY ()` needs a two-word owner.** `emptyLists` looks at the single
  token before `(`, which is `BY`, and bare `BY` is correctly vetoed. Keying
  owners on pairs (`ZORDER BY`, `SORTED BY`) fixes it; this folds naturally
  into the adjacency design below. Three cases.

## The next check: forbidden adjacency

Designed and measured but not built, so that the reasoning is not redone.
Full version in `docs/design-notes.md`; the short form:

The unit is an **ordered pair of adjacent significant tokens at bracket depth 0
within a fragment**, with `$` for end of fragment. `NEEDS_FOLLOWER` is the
special case where the second element is `$`. One mechanism covers five things
that looked like five checks -- truncation (`TO $`), a missing mid-statement slot
(`TABLE COMPUTE` in `ANALYZE TABLE COMPUTE STATISTICS`), exclusive alternatives
(`ALL DISTINCT`, `EXTENDED CODEGEN`), compound-statement shape (`BEGIN LOOP`,
`ATOMIC END`), and a missing required modifier (`OR VIEW`). Measured yield: **66
of the 208 currently-missed must-reject cases**, from 65 distinct pairs.

A pair ships only after three gates, in order:

1. **generated** as a candidate by `scripts/derive_shape_sets.py` -- occurs in a
   missed must-reject case, in no valid SQL;
2. **confirmed** against the page's verbatim `syntax:` block via the case's
   `omits:` or `conflicts:` field, which must name a mandatory slot or an
   exclusive pair. The docs are the oracle; frequency is not;
3. **vetoed by data** forever -- absent from the 562 valid files and 823
   must-parse cases, re-checked every run.

Gate 2 is the one that cannot be skipped: admitting pairs by statistics alone
fires on 21.8% of valid statements (measured, `docs/design-notes.md`). The
shipped artifact is an explicit deny-list with a reason and a case id per entry,
so new Databricks syntax cannot make it fire.

Boundaries fixed at design time: it may check that a slot between two clause
keywords is **non-empty**, never what is **inside** it; it may check adjacency
and order, never build a statement model or resolve names; a pair whose two
words could both be identifiers in the position tested is refused, not tuned.
Adding it needs a fourth `shape_of` bucket (`conflict`), since 14 of the
exclusive-alternative cases currently sit in `grammar` and would otherwise move
the target denominator silently.
