# databricks-sql-quickcheck

Guidance for AI coding agents working in this repo. The workspace index is
`../AGENTS.md`. Read that first for the standing constraints, which apply here
too: no employer SQL, ever, and no work compute.

Last updated 2026-09-25 (statement-shape checks added the same day).

## What this is

This is a fast, shallow syntax checker for Databricks SQL. It is a single-pass
lexer plus structural checks, written in TypeScript with no runtime
dependencies, and it ships as three things: a VS Code extension, a CLI and a
library. It is the as-you-type tier. SQLFluff (`../sqlfluff`) is the
full-grammar tier, run on save or in CI. Don't grow this into a grammar: every
grammar rule added is a way to be wrong about valid SQL.

```
src/lexer.ts      token boundaries: strings, quoted identifiers, comments, $$ bodies,
                  templates, notebook cell separators. Nothing statement-level.
src/check.ts      token-level checks (brackets, commas, operators, lists), run per fragment
                  (tokens between `;` / cell separators)
src/statements.ts statement-shape checks: keyword typos, missing `;`, column-definition
                  commas, clause order, CASE structure, dangling keywords
src/common.ts     shared types and token helpers
src/keywords.ts   GENERATED by scripts/gen_keywords.py -- do not edit by hand
src/cli.ts        dbsql-quickcheck: files, --stdin, --json, --jsonl batch mode
src/extension.ts  VS Code: diagnostics on open/change (40 ms debounce), in-process
src/test/         node:test unit tests
eval/evaluate.py  the corpus evaluation (run with ../databricks-sql-corpus/.venv)
examples/         mistakes.sql: one mistake per statement, the README's sample output
```

## The invariant

**An error must never fire on valid SQL.** A false positive on every keystroke
is worse than no checker. Before any change to `lexer.ts`, `check.ts` or the
keyword list is done:

```bash
npm test
../databricks-sql-corpus/.venv/bin/python eval/evaluate.py
```

The evaluation must still report `0` error files and `0` warning files on the
valid corpus, and `823/823` clean must-parse reference cases (the count grows
as the corpus does). Its exit status is non-zero on any false positive, and 2
if its known-bad control stops firing. It also reports catch rates. On the
corpus's own `mutate.py` mutants the guaranteed tier is at 100.0%. On
everyday mistakes made to the clean files it is 95% of keyword typos, 94% of
deleted `;` and 96% of deleted column commas (all as of 2026-09-25). A change
that trades a false positive for recall is the wrong trade.

Also run the adversarial pass over Spark's own test suite (`spark-sql-tests`,
304 files of unusual syntax, unscored because it mixes valid and invalid
statements). On 2026-09-25 the statement-level checks found exactly two things
there, both real. It is where the `EXPLAIN FORMATTED` newline and
pipe-`AGGREGATE` alias false positives were found, and no other set had them.

The first version was tuned only against `mutate.py` and scored 100% there,
but it caught 7 of 30 everyday mistakes when Tom typed into a real file. The
mutation generator only makes bracket, quote, comma and operator damage.
Measure against mistakes people make (`everyday_mutants` in the evaluation),
not only against the generator you have.

Every check needs two tests: a case that must fire, and the valid Databricks
construct that looks most like the mistake, which must stay quiet. Examples:
`ARRAY<INT>)` next to `a >)`, `count(*) total` next to `a b c`.

## Severity

- **error**: no grammar can accept it (brackets, quotes, `,,`, a dangling
  operator, `CASE` without `END`).
- **warning**: Spark's non-reserved keywords mean the parser might accept it
  (`SELECT a, FROM t` can read as a column named `from`), or it is valid SQL
  that does the wrong thing (`SELECT a\n  b`).

Heuristic checks are warnings. They only run on fragments with no errors,
because they depend on bracket depths.

## Things that cost time to get right

- **A word one letter off a keyword proves nothing on its own.** Databricks
  lets nearly every keyword be a name, and real schemas have columns called
  `form`, `pull`, `target`, `name`. A typo is reported only with positional
  evidence:
  - between two complete operands, where no name can go (`SELECT a FORM t`);
  - before a word that only follows a keyword (`ORDRE BY`, `CAES WHEN`);
  - after a keyword whose next word is fixed (`LEFT JION`, `IS NUL`).

  `CONTINUES` (keywords that cannot end an expression) and `STRUCTURAL`
  (keywords that cannot begin one) in `statements.ts` define "operand" as a
  blocklist, precisely because so many keywords are used as names.
- **A same-line implicit alias (`SELECT a b, c`) is not warned by default.**
  250 deliberate uses were found in 50 of 510 valid files. It is opt-in
  (`explicitAliases`) for teams that require AS.
- **`Chapter08/Clean Up.sql` is broken as published.** Its `USE CATALOG` has no
  `;` before the next statement. The corpus's `docs/gaps.md` records it as a
  source-side error, and SQLFluff agrees. `KNOWN_BROKEN` in the evaluation
  scores it the other way round (quickcheck must flag it). Add a file there
  only with that kind of independent confirmation.

- **Keywords decide the missing-comma heuristics.** A word in `KEYWORDS` is
  never treated as a bare identifier, so a word missing from the set can cause
  false positives. `OFFSET` and `MEASURES` did, because SQLFluff's lists lack
  them. An extra word only costs recall. Add words to `EXTRA` in
  `scripts/gen_keywords.py` and regenerate with `npm run keywords`. Don't add
  common column names (`ID`, `NAME`, `VALUE`).
- **An alias on a new line is only a warning after a bare column.** TPC-DS
  writes `sum(case … end)` then `sun_sales` on the next line on purpose.
- **Notebook cells are hard boundaries.** Each cell runs on its own, so the
  lexer stops strings and comments at `-- COMMAND ----------`, but only in
  files with the `-- Databricks notebook source` header.
- **`SET key = value` is raw text to Spark.** `SET foo = (1, 3` is valid, so
  raw statements (`SET`, `RESET`, `ADD`, `LIST`, `REFRESH`, `DFS`) get lexical
  checks only. `SET VAR` is real SQL and is checked.
- **Hints are parsed by Spark.** `/*+ BROADCAST(t) */` is a comment to the
  lexer, but its brackets are checked when it follows
  `SELECT`/`INSERT`/`UPDATE`/`MERGE`/`DELETE`.
- **`mutate.py` mis-tiers `SET` mutants after a notebook header.** Its
  `_in_set_statement` doesn't skip SQLFluff's `notebook_start` token. The
  evaluation excludes those mutants explicitly, with a printed count, rather
  than scoring them. The one-line fix belongs in databricks-sql-corpus.

## Release and install

`npm run package` builds `dist/databricks-sql-quickcheck.vsix`, and
`code --install-extension` installs it. Nothing is published to the
